# Лента из открытых источников

Вторая утренняя рассылка бота. Восемь разделов в одном письме: экраны недели
с Mobbin, сайты дня CSS Design Awards, кейсы студий, Behance, Dribbble,
DProfile, награды Made on Tilda, новые приложения Snapensnap.

```bash
python -m inspobot.feed            # собрать и отправить
python -m inspobot.feed --list     # состав, без единого запроса
python -m inspobot.feed --probe    # что отвечает каждый источник
python -m inspobot.feed --dry-run  # показать в консоли
```

**Claude здесь не участвует.** Ни ключа Anthropic, ни пакета `anthropic` —
это проверяется тестом (`tests/test_feed.py::LayerTests`), а не обещанием:
если какой-нибудь импорт снова притянет `daily.py`, прогон покраснеет. Раздел
Mobbin ходит на их MCP-сервер напрямую, токеном, который и так выписан на
этот сервер. Прогон стоит трафик.

---

## Устройство

Четыре слоя, и границы между ними — не стиль, а условие проверяемости.

| Файл | Отвечает за | Сеть |
|---|---|---|
| `sources.py` | объявление источников: адрес, способ, карта полей | нет |
| `harvest.py` | разбор: RSS/Atom, JSON, ссылки, og-теги | нет |
| `fetcher.py` | скачивание, robots.txt, паузы, скриншоты | да |
| `mcp_client.py` | JSON-RPC к MCP поверх streamable HTTP | да |
| `gather.py` | очередь способов, память, ротация, склейка разделов | через них |
| `feed.py` | отправка, память, команды | через них |

`harvest.py` не импортирует ни `httpx`, ни `sqlite3` — и это тоже
закреплено тестом. Поэтому весь разбор проверяется на сохранённых страницах,
без сети, а прогон из 525 проверок идёт две с половиной секунды.

## Источник — это запись, а не код

```python
Source(
    key="cssda",
    section="cssda",
    title="Site of the Day",
    url="https://www.cssdesignawards.com/wotd-award-winners",
    ways=("html",),
    link_re=r"cssdesignawards\.com/sites/[^/\"'?#]+/\d+",
    limit=3,
    shot=True,
)
```

Сайт перевёрстан — правится одна строка. На сервере правится вообще без
выката, файлом `var/sources.json`.

### Способы разбора

Источник перечисляет их в `ways`; `gather` идёт по списку и останавливается
на первом, который вернул хоть что-то.

* **`rss`** — лента. Самый честный способ: сайт сам отдаёт машиночитаемое.
  Разбираются и RSS 2.0, и Atom; картинка берётся из `enclosure`, `media:*`
  или первой `<img>` в описании — именно в таком порядке, потому что `<img>`
  из описания часто оказывается счётчиком в один пиксель.
* **`json`** — внутренняя ручка сайта. `items_path` — путь к массиву,
  `fields` — карта полей, `url_template` — если готовой ссылки нет, а есть
  `id` и `slug`. В пути можно перечислить запасные варианты через `|`:
  `covers.original|covers.404` переживает переименование поля молча.
* **`html`** — выгрести со страницы все ссылки под регулярку и дочитать
  заголовок с картинкой из og-тегов самой находки.
* **`mobbin`** — не HTTP, а вызов инструмента MCP. Подробности ниже.

**Почему у большинства источников `html`, а не аккуратный разбор вёрстки.**
Семь сайтов — это семь парсеров, которые ломаются семью разными способами, и
каждый раз молча. Одна регулярка на ссылку плюс общие для всего веба
og-теги дают ту же карточку, а когда всё-таки ломаются — ломаются одинаково,
и видно это одной командой.

### Когда картинки нет

`shot=True` заказывает снимок страницы через mShots (без ключа и
регистрации). Осмысленно для наградных списков: там находка и есть сайт
целиком. Заменить сервис — `INSPOBOT_SHOT_URL` с подстановкой `{url}`,
выключить совсем — `INSPOBOT_FEED_SHOTS=0`.

Если картинки нет и снимок не заказан, находка уходит текстом со ссылкой.
Молча пропускать нельзя: именно так раздел из четырёх кейсов превращается в
раздел из одного, и это не видно ни в логе, ни в письме.

## Раздел Mobbin: что он на самом деле показывает

**У поиска Mobbin через MCP нет ни сортировки по популярности, ни окна «за
неделю».** Инструмент `search_screens` принимает `query`, `platform`,
`limit`, `page`, `exclude_screen_ids`, `mode`, `image_format`, `task_intent`
— и всё. Ни `sort`, ни `time`. В ответе приходит `id`, `image_url`,
`mobbin_url`, `app_name`, `platform` — ни лайков, ни даты, ни просмотров.

Поэтому раздел называется **«Mobbin — экраны недели»**, а не «самое
популярное»: каждую неделю берётся следующая формулировка из списка в
`mobbin_feed.THEMES`, Mobbin возвращает лучшее по ней своим ранжированием,
уже показанное исключается. Это та же оговорка, что в README про B2B/B2C:
разделение сделано формулировками запроса, а не фильтром, которого у Mobbin
нет.

Тема меняется **раз в неделю, а не раз в день** — иначе «тема недели» была
бы неправдой прямо в заголовке.

### Прямой доступ вместо коннектора

Первый дайджест (`inspobot.daily`) ходит в Mobbin через Claude: модель
подключается к их MCP-серверу, смотрит картинки и пишет разбор. Это стоит
токенов.

Лента ходит туда сама. Токен, который выдаёт `mobbin_auth`, выписан на сам
ресурс `https://api.mobbin.com/mcp` (RFC 8707, параметр `resource`) — то
есть предназначен этому серверу, а не Anthropic. `mcp_client.py` делает
рукопожатие MCP и один `tools/call`.

Тонкости, на которых такой клиент ломается, и что с ними сделано:

* `Accept: application/json, text/event-stream` — **на каждом** POST, включая
  уведомление `notifications/initialized`. Сервер, которому не хватает
  одного типа, отвечает 406 ещё до тела запроса.
* Ответ приходит либо JSON, либо потоком SSE — на том же адресе. Тип
  сравнивается по первой части заголовка: настоящий выглядит как
  `application/json; charset=utf-8`, и проверка на равенство его не узнаёт.
* В потоковом режиме `httpx` бросает `ResponseNotRead` на `.content`, пока
  тело не прочитано явно.
* Оборванный поток — **ошибка, а не пустой результат.** Иначе «поиск ничего
  не нашёл» и «связь оборвалась» выглядят одинаково.
* Переадресация не выполняется. `httpx` снимает `Authorization` при смене
  хоста, и ответ 401 оттуда читается как истёкший токен — а обновление по
  такому «истечению» сжигает refresh-токен на каждом запуске.
* На 401 токен обновляется **и записывается на диск**, ровно один раз.
  Supabase гасит прежний refresh-токен при каждом обмене: обновиться в
  памяти и не сохранить — значит завтра получить `refresh_token_already_used`
  и идти проходить вход через браузер.
* Договорились не о ревизии `2025-06-18` — клиент останавливается, а не
  делает вид, что понял. В следующих ревизиях оборванный поток продолжают
  через GET с `Last-Event-ID`, и без этого пустой ответ не отличить от
  потерянного.
* `mode="standard"`, не `deep`: `deep` запускает на стороне Mobbin перебор с
  оценкой каждого кандидата — долгий поток, который любит обрываться, а нам
  нужен короткий предсказуемый ответ раз в сутки.

Чего **не проверено**: ни один из этих запросов не уходил к живому
`api.mobbin.com` — из песочницы, где это писалось, egress-политика рубит
соединение (403 на CONNECT). Проверено рукопожатие целиком на подставном
транспорте: порядок вызовов, заголовки, перехват сессии, обе упаковки
ответа, 401, чужая ревизия, переадресация. Первый живой запрос — на сервере,
командой `--probe --only mobbin`.

## Студии: список, который пополняется

`config/studios.txt`, по строке на студию:

```
Название | адрес списка работ | регулярка ссылки кейса | сколько брать
```

Последнее поле необязательно, по умолчанию 1. Свой список — в
`var/studios.txt`: он читается первым и заменяет встроенный целиком.
Кривая строка называет себя по номеру и не роняет остальные.

Порядок внутри раздела каждый день сдвигается на один. Без этого раздел на
четыре места, в котором десять студий, каждый день показывал бы первые
четыре: память не даёт повториться кейсу, но не мешает одной и той же студии
занимать место вечно.

## Правки без выката: var/sources.json

```json
{
  "sources": {
    "dprofile": { "url": "https://dprofile.ru/cases", "limit": 5 },
    "snapensnap": { "enabled": false }
  },
  "studios": [
    { "title": "Новая", "url": "https://new.ru/work/", "link_re": "new\\.ru/work/" }
  ],
  "add": [
    {
      "key": "awwwards",
      "section": "cssda",
      "title": "Awwwards",
      "url": "https://www.awwwards.com/websites/",
      "link_re": "awwwards\\.com/sites/[^\"'?#]+",
      "shot": true
    }
  ]
}
```

Ошибка в файле — это падение с именем файла и строкой при загрузке, а не
молчаливый пропуск источника: письмо без раздела заметят через неделю, а
падение с текстом — в тот же день. Правка, оставившая `html` без `link_re`,
тоже не пройдёт: такой источник выгреб бы всю навигацию сайта.

## Как чинить сломавшийся источник

```bash
python -m inspobot.feed --probe --only dribbble --save /tmp/pages
```

Построчно: что спрашивали, что ответили, сколько ссылок нашлось, сколько
взято, и пример. `--save` кладёт скачанные страницы на диск.

Чинить разбор по живому сайту невозможно: страница меняется между двумя
запусками, и непонятно, правило поправилось или сайт. По сохранённому файлу
правило правится за минуту и закрепляется тестом — так сделаны все фикстуры
в `tests/test_harvest.py`.

Код возврата `--probe` равен 1, если лента вышла пустой. Пустая лента — не
успех прогона, и cron должен это знать.

### Что уже известно про конкретные источники

| Источник | Состояние |
|---|---|
| CSS Design Awards | адрес находки подтверждён: `/sites/<слаг>/<номер>/` |
| DProfile | адрес кейса подтверждён: `/case/<номер>/<слаг>`; список — «Выбор жюри» |
| Made on Tilda | награду получает внешний сайт, поэтому правило — «что угодно, кроме самой Тильды» |
| Behance, Dribbble | правила написаны по известной форме адресов, вживую не проверялись |
| Snapensnap | **адрес не подтверждён** — поиском сайт не находится; раздел будет пустым, пока `--probe` не покажет настоящий |
| Mobbin | форма ответа снята с живого инструмента; транспорт вживую не проверялся |

Ни один HTTP-источник не проверялся живым запросом: в песочнице, где это
писалось, egress-политика рубит все семь доменов (403 на CONNECT). Разбор,
память, ротация, склейка и отправка проверены тестами; адреса и регулярки —
нет. Первый прогон `--probe` на сервере покажет, какие из них угаданы верно.

## Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `INSPOBOT_SOURCES` | `var/sources.json` | правки поверх встроенного списка |
| `INSPOBOT_STUDIOS` | `var/studios.txt` | свой список студий |
| `INSPOBOT_FEED_IMAGE_MODE` | `photo` | `document` — без сжатия |
| `INSPOBOT_FEED_SHOTS` | `1` | заказывать снимок, если картинки нет |
| `INSPOBOT_SHOT_URL` | mShots | свой сервис снимков, с `{url}` |
| `INSPOBOT_FEED_ROBOTS` | `1` | уважать robots.txt |

Картинки по умолчанию идут **фотографиями**, а не файлами: у ленты это
обложка кейса и снимок сайта, а не скриншот с мелким текстом — сжатие им не
вредит, а плиткой в чате они читаются лучше.

## Память

Отдельная от памяти первого дайджеста, по нормализованному адресу
(`harvest.link_key`): схема и хост к нижнему регистру, `www.` снимается,
хвостовой слэш убирается, метки кампаний выбрасываются, остаток запроса
сортируется. Один и тот же кейс из ленты и со страницы-списка не приходит
дважды.

Память полная, а не скользящая, как у Mobbin: там окно в сто значений
диктовал предел API, здесь ограничения нет, а строка занимает полсотни байт.

Записывается **до** отправки: повтор после половины доставленной ленты хуже,
чем пропуск одной находки.
