# VPN на том же сервере: VLESS + Reality

Тот же Netcup, где живёт бот. Xray встаёт на 443/tcp, бот не слушает
ни одного порта — он только сам ходит наружу, — поэтому рассылка в
11:00 и кнопки продолжают работать как работали.

## Почему Reality, а не WireGuard

WireGuard опознаётся по сигнатуре первого пакета: российские ТСПУ
режут его на магистрали, независимо от того, где стоит сервер. Reality
такой сигнатуры не даёт. Клиент начинает настоящее TLS-рукопожатие с
реальным чужим сайтом (в конфиге он называется маскировочным доменом),
и только внутри уже установленного соединения открывается туннель.

Снаружи это неотличимо от похода на этот сайт. Активная проверка тоже
ничего не даёт: если постучаться на 443 без ключа, Xray молча проксирует
запрос на настоящий сайт, и проверяющий видит его, а не VPN.

## Установка

Одна команда на сервере:

```bash
cd ~/inspobot && git pull && sudo sh deploy/vless.sh install
```

Скрипт сам: поставит пакеты, определит внешний адрес, подберёт рабочий
маскировочный домен, установит Xray, сгенерирует ключи, соберёт конфиг,
запустит службу и напечатает ссылку с QR-кодом для первого клиента.

Минут пять, вопросов не задаёт.

Первого клиента зовут `phone`. Другое имя — аргументом:

```bash
sudo sh deploy/vless.sh install vlad-iphone
```

## Клиенты

```bash
sudo sh deploy/vless.sh add masha       # ссылка и QR для нового человека
sudo sh deploy/vless.sh link masha      # показать ссылку ещё раз
sudo sh deploy/vless.sh list            # все, кто есть
sudo sh deploy/vless.sh remove masha    # отобрать доступ
sudo sh deploy/vless.sh status          # жив ли сервер
sudo sh deploy/vless.sh repair          # пересобрать конфиг и починить права
sudo sh deploy/vless.sh check           # почему не подключается
sudo sh deploy/vless.sh selftest        # пройти через туннель самому
sudo sh deploy/vless.sh diagnose        # перебрать варианты
sudo sh deploy/vless.sh set-domain X    # сменить маскировочный домен
sudo sh deploy/vless.sh probe-links     # ссылки на несколько доменов сразу
sudo sh deploy/vless.sh probe-clear     # убрать пробные входы
sudo sh deploy/vless.sh reset           # снести лишнее, оставить один вход
sudo sh deploy/vless.sh v6              # ссылки на IPv6
sudo sh deploy/vless.sh set-host АДРЕС  # другой адрес в ссылках
sudo sh deploy/vless.sh transport xhttp # сменить транспорт основного входа
sudo sh deploy/vless.sh ss              # вход Shadowsocks (без рукопожатия TLS)
sudo sh deploy/vless.sh ss-clear        # убрать его
sudo sh deploy/vless.sh cdn ДОМЕН       # маршрут через Cloudflare
sudo sh deploy/vless.sh cdn-check       # Cloudflare достаёт до сервера?
sudo sh deploy/vless.sh cdn-clear       # убрать маршрут через CDN
```

У каждого человека **свой** клиент. Не потому что жалко, а потому что
иначе отобрать доступ у одного нельзя, не сломав всем остальным: ключ
общий. С отдельными клиентами `remove` выключает ровно одного.

## Что ставить людям

| Где | Приложение |
|---|---|
| iPhone, iPad | **v2RayTun** или **Streisand** (обе есть в российском App Store) |
| Android | **v2rayNG** или **Hiddify** |
| macOS | **Hiddify** или **V2Box** |
| Windows | **Hiddify** или **v2rayN** |

Ссылка `vless://…` вставляется из буфера — в любом из них есть кнопка
«импорт из буфера обмена». QR сканируется камерой внутри приложения.
Если QR в терминале не читается (тёмная тема, мелкий шрифт), просто
отправьте ссылку текстом: клиенты понимают её целиком.

## Чинить, если не подключается

```bash
sudo sh deploy/vless.sh status
sudo journalctl -u xray -n 50 --no-pager
```

**`permission denied` на config.json в журнале, служба не стартует** —
Xray работает не от root, а от `nobody`, и закрытый конфиг ему не
открыть. Лечится одной командой:

```bash
sudo sh deploy/vless.sh repair
```

Она пересобирает конфиг с правами 0640 root:nogroup, поднимает службу и
печатает ссылки всех клиентов. Шпаргалка с приватным ключом при этом
остаётся 0600 — её Xray не читает.

**`Special user nobody configured, this is not safe!`** — это ворчание
systemd на юнит от штатного установщика Xray, а не ошибка. Служба с ним
работает.

**Служба активна, порт слушается, а клиент не цепляется** — почти
всегда время на сервере разъехалось с реальным: TLS этого не прощает.
`timedatectl` покажет, `apt install -y systemd-timesyncd` починит.

**Работало и перестало у всех сразу** — возможно, маскировочный домен
заблокировали или он перестал отвечать. Поменять:

```bash
sudo sh deploy/vless.sh set-domain dl.google.com
```

Команда сначала проверяет домен настоящим рукопожатием и меняет его
только если оно прошло. Ссылки клиентов после смены **перестают
работать** — домен зашит в каждую, — поэтому она сразу печатает новые.

Не знаете, какой домен взять, — переберите:

```bash
sudo sh deploy/vless.sh diagnose
```

**Не подключается у кого-то одного** — сначала выясните, чья это
сторона. Со своего компьютера (не с сервера):

```bash
sh deploy/test-link.sh 'vless://…'
```

Скачивает Xray во временный каталог, поднимает клиента по этой самой
ссылке и выходит наружу. Показал адрес сервера — ссылка и сервер
исправны, дело в чужом приложении или провайдере. Не прошло — дело в
связке, и приложение ни при чём.

**Перед запуском закройте все VPN-клиенты на этой машине** — именно
закройте, а не отключите соединение. Happ и подобные выставляют
системный прокси на 127.0.0.1, и тогда в проверку течёт весь трафик
машины: вывод будет про них, а не про вашу ссылку. Скрипт это ловит
(сначала проверяет прямой выход, потом считает лишние соединения), но
надёжнее просто закрыть.

Заблокирован ли адрес там, откуда подключаются:

```bash
sudo sh deploy/vless.sh reach            # с узлов внутри России
sudo sh deploy/vless.sh reach "443 8443" # и по портам
```

Ни один узел не достучался — менять домен бесполезно, блокируется
адрес или порт. Достучались все — адрес чист, ищите дальше.

**Ничего не подключается, а сервер выглядит здоровым** — начните с этого:

```bash
sudo sh deploy/vless.sh check      # семь причин разом
sudo sh deploy/vless.sh selftest   # пройти через туннель с самого сервера
sudo sh deploy/vless.sh diagnose   # перебрать варианты по одному отличию
```

`diagnose` поднимает рядом, на запасном порту, такой же сервер и гоняет
через него варианты, отличающиеся ровно одной вещью: другой домен,
другой отпечаток ClientHello, без Vision, пустой shortId. Живую службу
не трогает. Что заработало — то и было причиной.

**Работает у одного, не работает у другого** — это не сервер. Сначала
проверьте, что у второго в приложении включён именно `xtls-rprx-vision`
и импорт прошёл целиком (ссылку часто обрезают при копировании).

## Про маскировочный домен

К домену, за которым прячется Reality, два независимых требования, и
провал по любому выглядит одинаково: сервер здоров, никто не подключается.

**Требование первое: ответ меньше 8 КиБ.** Reality отдаёт клиенту не свой
ответ, а ответ настоящего сайта. В модуле `reality`, закреплённом в
Xray 26.x, буфер под этот ответ равен 8192 байта (`tls.go:140`), и запись
длиннее обрывает рукопожатие — уже **после** успешной аутентификации.

Так и вышло с `www.microsoft.com`: поверхностную проверку он проходит
безупречно (TLS 1.3, ALPN h2, посторонний видит настоящий сертификат
Microsoft), а запись Certificate у него ~8273 байта из-за длинной цепочки
с OCSP. В журнале при этом только `REALITY: processed invalid connection
... handshake did not complete successfully` — и это сообщение обманывает:
оно последнее из шести веток и достижимо **только** когда ключи, shortId,
SNI и часы уже приняты. Поэтому ни перегенерация ключей, ни NTP, ни
пустой shortId ничего не меняют.

Замерить домен:

```bash
python3 deploy/vless_domains.py www.microsoft.com dl.google.com
```

**Требование второе: домен не заблокирован там, откуда подключаются.**
Reality притворяется трафиком к этому домену — если провайдер клиента
режет сам домен, он срежет и туннель. Домен, идеальный для сервера в
Германии, может не годиться для пользователя в России. Это проверяется
только с той стороны:

```bash
sudo sh deploy/vless.sh probe-links
```

Команда поднимает несколько пробных входов на запасных портах, каждый со
своим доменом, и печатает по ссылке на каждый. Человек на той стороне
импортирует все и пробует по очереди; какая подключилась — тот домен и
проходит. Без этого на каждый домен уходит круг переписки. Потом
`probe-clear` убирает пробные входы.

Установщик подбирает домен замером и **настоящим рукопожатием**, а не
проверкой доступности. Это дольше на минуту и избавляет от разбора,
который иначе занимает вечер.

Рабочие на сегодня: `dl.google.com`, `www.bing.com`, `www.samsung.com`,
`www.apple.com`, `addons.mozilla.org`. Свой: `VLESS_SNI=example.com` перед
установкой или `set-domain` потом.

## Когда помечен адрес: IPv6

Признак: не проходит **ни один** протокол — ни REALITY поверх TCP, ни
поверх xhttp, ни Shadowsocks, у которого рукопожатия TLS нет вовсе, — а
TCP при этом устанавливается. Когда валятся все протоколы сразу, дело
не в протоколе: у оператора заблокирован приём данных на конкретный
адрес.

Проверяется это сравнением: если у работающего сервиса узел в той же
стране и на той же схеме из этой сети работает, а наш нет, остаётся
одно отличие — адрес.

Помогает не смена протокола, а смена адреса. И самый дешёвый запасной
адрес обычно уже есть: хостеры выдают вместе с сервером целый блок
IPv6 (`/64`). Списки блокировок построены вокруг IPv4, фильтрация IPv6
у многих операторов слабее или отсутствует, а адресов в блоке столько,
что кончиться они не могут.

```bash
sudo sh deploy/vless.sh v6
```

Находит глобальный адрес IPv6, при необходимости пересобирает конфиг на
двойной стек и печатает ссылки на него. Прежние ссылки на IPv4
продолжают работать — они не заменяются.

Все входы слушают `::`, а не `0.0.0.0`: первое принимает и IPv6, и
IPv4, второе — только IPv4.

Оговорка: у человека на той стороне должен быть IPv6. У мобильных
операторов он обычно есть, у домашних провайдеров реже. Если его нет,
такая ссылка не подключится — и это не поломка сервера.

За деньги есть и второй путь: дополнительный IPv4 у хостера (пара евро
в месяц) и `set-host` на него. Но если помечен весь диапазон хостера, а
не один адрес, соседний IPv4 не поможет — в отличие от IPv6, который
лежит в совсем другом пространстве.

## Транспорт: xhttp вместо голого TCP

Голый TCP с Vision (`xtls-rprx-vision`) — самая узнаваемая связка:
фильтры научились определять её по рисунку трафика, не читая
содержимого. Показательно, как устроены рабочие узлы известных
сервисов: VLESS · **xhttp** · Reality, VLESS · xhttp · TLS,
VLESS · WebSocket · TLS. Голого TCP среди них нет.

xhttp заворачивает поток в обычные HTTP-запросы поверх того же REALITY:
маскировка, ключи и домен остаются, меняется только форма трафика — она
становится браузерной. Домен для этого не нужен.

```bash
sudo sh deploy/vless.sh transport xhttp   # переключить
sudo sh deploy/vless.sh transport tcp     # вернуть
```

Vision при этом снимается принудительно: с xhttp он несовместим. Ссылки
меняются, команда печатает новые.

Пробные входы (`probe-links`) остаются на TCP намеренно: они нужны для
перебора доменов, и если бы вместе с доменом менялся транспорт, перебор
проверял бы две переменные разом.

## Когда убивают рукопожатие TLS: Shadowsocks

Симптом: TCP до сервера доходит (в журнале видно соединения с адреса
человека), а в ответ на каждое — `failed to read client hello`. На любом
порту, с любым маскировочным доменом, с любым отпечатком, даже из голого
браузера по `https://IP`. Значит, DPI выбрасывает пакет с рукопожатием
TLS, и всё, что начинается с TLS, на этом адресе мертво.

У Shadowsocks рукопожатия TLS нет вовсе: с первого байта идёт поток
случайных на вид данных, опознавать нечего. Ставится тем же Xray:

```bash
sudo sh deploy/vless.sh ss        # по умолчанию на 443
```

443 не случайно: нестандартные порты операторы закрывают чаще, а на 443
TCP обычно проходит. REALITY при этом уступает порт и уезжает на 8443 —
его ссылки меняются, команда печатает новые. Тем, кого не режут, REALITY
остаётся и работает как работал.

Ссылку `ss://` отправлять туда, где REALITY не проходит. В Happ она
импортируется так же, из буфера, но протокол в профиле будет
Shadowsocks, а не VLESS.

Метод — `2022-blake3-aes-128-gcm`: единственное семейство без известных
способов опознания по трафику. Старые методы (`aes-256-gcm` и прочие)
DPI различает, и тогда вход теряет смысл.

Убрать: `sudo sh deploy/vless.sh ss-clear`.

Xray 26 при запуске предупреждает, что Shadowsocks устарел в пользу
VLESS Encryption — это правда, у SS нет forward secrecy. Но VLESS
Encryption совсем свежий, и поддержка в клиентах пока неровная;
Shadowsocks понимают все. Работает — и ладно.

## Когда режут сам адрес: маршрут через CDN

Бывает, что DPI оператора режет **любой** TLS к адресу сервера: TCP
проходит, а первый же пакет с ClientHello выбрасывается — на любом
порту, с любым доменом, с любым отпечатком, даже из голого Safari. В
журнале сервера это выглядит как `failed to read client hello` на
каждой попытке. На этом адресе REALITY для такого оператора мёртв, и
крутить настройки бессмысленно: до сервера просто нельзя ходить.

Выход — не ходить на него. Человек подключается к адресу Cloudflare
(для DPI это обычный сайт за CDN), а Cloudflare сам ходит на наш
сервер. Нужен домен (~$10 в год) и бесплатный Cloudflare.

**В Cloudflare:** добавить домен, переключить у регистратора
nameserver'ы на выданные, дождаться Active. Потом:

- DNS → запись `A`, имя `@`, адрес сервера, Proxy status — **Proxied**
  (оранжевое облако; серое — значит люди пойдут прямо на наш IP, и всё
  зря);
- SSL/TLS → режим **Full** (не Flexible: тогда между Cloudflare и
  сервером трафик пойдёт открытым; и не Full strict: наш сертификат
  самоподписанный).

**На сервере:**

```bash
sudo sh deploy/vless.sh cdn vpn.example.com   # поднять вход
sudo sh deploy/vless.sh cdn-check             # Cloudflare достаёт до нас?
```

Вход — VLESS поверх XHTTP + TLS на 443; REALITY при этом переезжает на
8443 и продолжает работать для тех, кого не режут. XHTTP, а не
WebSocket: Xray 26 объявил WebSocket устаревшим, а XHTTP как раз
задуман для CDN — режим `packet-up` шлёт данные обычными
HTTP-запросами, которые Cloudflare пропускает как есть.

Ссылки через CDN печатает `cdn-links`; людям в России раздавать их.
Проверить со своего компьютера: `sh deploy/test-link.sh '<ссылка>'` —
он понимает и такие ссылки.

Ограничение честное: Cloudflare в России под замедлением, скорость
через него будет ниже, чем напрямую. Зато доходит.

## Прибраться

Во время разбора входы накапливаются: пробные домены на своих портах,
Shadowsocks, CDN, сменённый транспорт. Потом это мешает — лишние
открытые порты и непонятно, какая ссылка от чего.

```bash
sudo sh deploy/vless.sh reset
```

Оставляет один вход: REALITY поверх TCP с Vision на 443, новые ключи,
один клиент. Адрес и маскировочный домен сохраняются — они проверены;
ключи, пути и порты перевыпускаются. Спрашивает подтверждение: все
прежние ссылки после этого недействительны.

AmneziaWG снимается отдельно, он живёт сам по себе:

```bash
sudo sh deploy/awg.sh uninstall
```

## Что внутри

Конфиг собирается скриптом `deploy/vless_admin.py` из файла
`/usr/local/etc/xray/reality.json` — там ключи, домен и список клиентов.
Сам `config.json` каждый раз генерируется заново: править живой конфиг
по месту значит каждый раз рисковать уронить сервер опечаткой в JSON.

Три решения, принятых за вас:

- **Журнал посещений не ведётся** (`"access": "none"`). На диске не
  копится, кто куда ходил. И приватность, и место: такой журнал растёт
  быстрее всего остального на сервере.
- **Локальная сеть сервера закрыта.** Иначе клиент по туннелю достаёт
  `127.0.0.1` этой машины, а там бот, его база и SSH.
- **Торренты заблокированы.** Жалоба хостеру прилетает на адрес, общий
  с ботом: заблокируют машину — встанет и рассылка.

## Что стоит знать заранее

**Адрес общий у вас и у бота.** Для личного использования нормально, но
это адрес дата-центра: Google иногда показывает капчу, часть стримингов
такие адреса режет.

**Если это станет сервисом — заведите отдельный сервер.** Не из-за
нагрузки (её нет), а из-за абуз: одна жалоба в Netcup блокирует машину
целиком, вместе с ботом. Пока это вы и несколько друзей — общая машина
в порядке.

**Netcup разрешает личный VPN**, но не разрешает публичный сервис и
торренты. Второе скрипт закрывает сам, первое — на вашей совести.

**Правовая сторона.** В России с марта 2024 запрещена реклама и
популяризация средств обхода блокировок — штрафы по КоАП. Сам по себе
VPN для личного использования не запрещён, но публичная раздача доступа
и тем более продажа — зона, где риск несёте вы, а не пользователи. Если
планируете что-то за деньги, это стоит обсудить с юристом, а не со мной.
